# Vimny — Architecture & Conventions

Vim-teaching dungeon crawler (Python/blessed). Dungeons are text buffers; every puzzle is solved with Vim commands. Curriculum: `vimny/content/levels.py`. Design vision/UI: `docs/SPEC.md`.

Admin features: `:edit` enters editor mode on any dungeon; `:save <name>` writes layout to `~/.Vimny/layouts/<name>.json` for use as level-design reference. The **forge** (`forge/` in the overworld, admin-only) goes further: it authors a shareable community level end to end without leaving the game — see "The forge" below and `docs/AUTHORING.md`.

## Rune scatter (generation)
- **Glyph source of truth**: `vimny/generation/room_gen.RUNE_CHAR` (kind → glyph); `dungeon_gen` imports it as `_RUNE_CHAR`. Rune run length is normalized to **1.._RUNE_MAX_LEN (=7) for every kind** via `_make_rune_syms`.
- **`_scatter_row(composite, rng, row, c_start, c_end, kinds, blocked=…)`** is the single scatter primitive: **greedy fill** (no density knob), random kind + length, **exactly one blank column between runs**, inclusive right edge. A run overrunning the edge is **clamped** to fill the remaining space (or one short — trailing space); **never two consecutive length-1 runs** (at the right edge it stops and leaves a trailing space rather than rewriting the penultimate run). Used by `_place_runes_in_room`, `_make_rune_corridor`, `_cataracts_place_zone`; `_tile_line_hall` follows the same rule with a forced non-void first run.
- **void only where a path is guaranteed**: only `_place_runes_in_room`'s default kind set includes `void`. The first cave greedy-fills with void then calls **`_carve_void_path(composite, protected=…)`** — BFS a floor route (routing around `protected` guard cells) and delete void runs on it — to guarantee solvability. Other scatter zones use the void-free word set (`_WORD_RUNE_KINDS`).
- **Deliberate non-normalized spacing**: The WORD Forge's `_l7_fill_row` keeps a **2–3 cell gap** on purpose — that spacing is what makes small-word `w` ≡ WORD `W`, which is the level's lesson. Don't normalize it to gap 1.

## Design principles

These are the rules a new level must satisfy. They are collected here, rather
than left as comments beside the level that first taught them, so that they can
be argued with as a set — a principle nobody can restate outside the code it
justifies is not a principle, it is a scar. Level-specific reasoning stays inline
in the builder; anything that generalises belongs here, and the inline copy
becomes a one-line pointer.

### PAR IS THE OPTIMUM — no exceptions

**Par is the cheapest route that exists, whatever that route turns out to be.**
If the optimum is a macro (`q`/`@`), a two-register setup, a `:g`, a counted
repeat, or a trick nobody planned for, *that* sets par. There is no level and no
wing where par may be pinned to "the route that teaches the lesson" while a
cheaper route exists — a par above the optimum hands two stars to mediocre play,
and to every route in between. If a level invites a shortcut, the shortcut is par.

**The budget then follows: `ceil(par × 1.4)`, always.** The budget is not a
design knob and is never hand-set to keep a favoured route alive. Forcing is by
par: a sub-optimal route loses a star, and if the standard budget also puts it
out of reach, that is the correct consequence, not a problem to tune around.

Two things follow that are easy to get wrong:
- **Moving par onto the shortcut does not cost you the lesson**, as long as the
  shortcut *contains* it. The Register II macro is par at 34, and its recorded
  body still pastes from both named registers — you cannot record it without
  having named the words first. Check that the optimum contains the lesson;
  don't retreat to a higher par to protect it.
- **Golf the tape before pinning par.** `G` at the end of a route is very often
  cheaper than `0 {n}j` (it lands on the gate row's spine, then `l` onto the
  exit), and a macro's recording should start at the *earliest* repeating
  opportunity — including the leading motion in the body, not before it.

**Do not golf it by eye — `python3 -m vimny.sharing jumpgolf` (2026-08-03).** Six
levels shipped a par that was not the optimum, every one of them because the
question was answered by reasoning: The Operator's Vault recorded 62 on the
argument that a counted jump only beats a walk when its count is a single digit
— true, and beside the point, because the jump never needed a count. The route
that existed was 55. The tool substitutes jumps for travel tokens, **collapses**
runs of them (`0 3j` → `G`), deletes dead travel, and replays the whole tape
through the real game loop for each candidate. Fixed this way: `wet_ink` 42→39,
`quartermaster` 15→14, `hall_of_echoes` 76→74, `operators_vault` 62→55,
`indentation_sanctum` 12→11, `stair_rail` 15→14. Five rules the tool is held to,
each of which was a bug first:
  - **Token gating is absolute.** Candidates are filtered against
    `known_commands(slug)` *and* the same set is handed to the replay. `G`/`gg`
    enter at curriculum position 10 and `H`/`M`/`L` at 11 — a level before that
    is correctly unimprovable, not unaudited, and the report must say which.
  - **A beat must hold at every terminal height.** `H`/`M`/`L` are
    viewport-relative while `room.rows > game_h`, so behaviour flips at
    `height == rows + 8`; `heights_for()` straddles exactly that line rather
    than sampling arbitrary numbers. Par must not become a function of the
    player's window. **`G`/`gg` read the buffer and are stable — usually the
    better answer for that reason alone**, and in a fogged level `G` means "as
    far down as the light goes", which is why one keyless jump serves four
    different drops in the Vault.
  - **A cheaper route counts only if the level still teaches its lesson.**
    Otherwise it is a **cheese to close, not a par to lower** — the distinction
    that kept `spellwrights_forge` at 44 (its `M` route skipped `&` on the level
    whose whole job is `:s`/`&`/`:g`; the seal was fixed instead). Some lessons
    are STATE, not keystrokes: `_VERIFY` holds `wet_ink`, whose par must assume
    a player who cannot read the saying until the braziers burn.
  - **Measure first, judge second.** Checking the lesson before replaying
    counted trials never shown to win and reported 86 imaginary cheeses.
  - **Say when the search stopped early.** A "no beat found" that hit its
    evaluation budget must not read like an exhaustive one.

  `tests/test_par_is_the_optimum.py` is the standing gate (opt-in:
  `VIMNY_JUMPGOLF=1`, or `=seeds` for every distinct layout across the repo's
  seeds — deduplicated by `layout_fingerprint`, since 49 levels × 6 seeds is only
  196 genuinely different builds). Its always-on tests guard the *guard*, which
  is what matters for a check run rarely — they found the lesson rule already
  rotted into a no-op on `shelving_room`. `tests/test_jumpgolf_search.py` is the
  positive control: the search is exercised against a cost landscape with a known
  answer, because "found nothing" and "cannot find anything" print the same. It
  showed that beam WIDTH and slack are needed together — slack alone loses the
  ridge to a tie-decoy. Solvers are covered from the other side by
  `tests/test_par_solvers_model_the_jumps.py`: a solver may not model a jump its
  level has not taught (a par no player can reach), and must model the buffer
  jumps it has (`_line_jump_moves`).

### FORCE BY GEOMETRY, NOT BY SURVIVAL

A level forces its lesson by making the puzzle *want* the new command — capacity,
shape, distance. It never forces by making the alternative lethal or by narrowing
the budget. "Two stars only with the new tool" teaches; "too tight to fumble"
punishes.

### NEVER LET ONE CLIP DO THE WORK OF TWO

For any level that teaches multiple registers, **no single clip may be wanted
anywhere**. Separate *rows* are not a guard — `J`, `dd`, `:m` and visual-block
all reshape rows, and a playtester who joins two rows and yanks once has defeated
capacity forcing without touching the lesson. The durable guard is content: two
texts that share no word, one word per target, so a combined clip is garbage by
construction and it does not matter how the player rearranges the source.

Related, for register levels specifically: **exchange beats addition.** A named
register costs `+2` per paste (see the prefix charge below) while a single-register
rival pays only extra travel, and travel is cheap because counts are cheap. So on
an *additive* puzzle named registers barely win. The shape that wins is exchange —
the paste lands in the hole the delete just made, welding the two operations
together so the rival cannot decouple them.

### THE REGISTER-PREFIX CHARGE

`"{reg}` is two real keypresses, so `main._register_prefix_cost(action)` adds 2 to
every operator (`_operator_cost`) and every paste charge; the audit's
`_token_ks_cost` matches (`"aye` = 4, `"ap` = 3). A named register buys
**persistence, not free typing**. Charging 0 would make named registers a pure
golf win and flatten the difficulty curve of every register level.

### SENSE, NOT DECREE — puzzle texts are texts the player knows

Puzzle text should be **well-known, public-domain** verse or prose whose structure
*is* the solution: the player repairs a text they already know by heart, so the
plaque demotes from decree ("make it say this") to confirmation. Copyrighted
lyrics are refused; religious texts are avoided. Shared pool: `vimny/content/proverbs.py`.

The test of it: the player must be able to *derive* the target state from the page
rather than be told it. The Culling Ledger's keep-lines all begin with the chain
word "that" — the rhyme's own signature — so `:v/that/d` is read off the page, not
decreed by a plaque.

### A PLAYABLE LINE MUST START WHERE ITS TEXT STARTS

`S`, `o` and `O` drop their typed line at the **segment start**. So in any room
where the player retypes a line, the floor segment must begin at the text column —
otherwise the retyped line lands misaligned and the checker rejects a correct
answer. Applies to every level using linewise insert.

### INTROS SET THE SCENE

The slug-keyed intro in `_LEVEL_INTROS` names the situation and the *feel* of the
verb. It never enumerates the level's wrongs, its fixes, or the command family
that solves it — discovering that is the puzzle. Keep them near the ~175-character
house median. The wizard poem recited *before* entry is where commands may be
named plainly. In-level banners follow the same rule, with one exception: a
message may name a key when it teaches how Vim is *applied to Vimny* (that a key
is picked up and pasted into a lock, that a door is opened with `:e`) rather than
which key solves the puzzle.

### BANNERS CARRY WHAT THE RENDER CANNOT

A message that describes a visible change is noise. If the reveal, the fall, or
the opening door is already animated, either drop the banner or replace it with
the part the screen cannot show — what it cost, what it woke, what is now
irreversible. Repeating events get told **once**.

## Par-solver toolkit (generation)

The per-level `_par_<slug>` solvers compute each dungeon's minimum-keystroke par. They share a toolkit at the top of `dungeon_gen.py` — supply a `neighbors(node)` generator; the machinery is shared:
- **`_dijkstra(start, is_goal, neighbors)`** / **`_bfs(...)`** — generic least-keystroke / uniform-cost search; return `(cost, prev, end_node)`, reconstruct with `_join_path`. Nodes must be orderable so heap/FIFO tie-breaks (hence the chosen path) match the old hand-written loops.
- **`_count_moves(passable, r, c, max_n, landable=None, dirs=_DIRS)`** — count-n `hjkl` (n=1→1 key, n>1→`len(str(n))+1`). `landable` lets a void cell block landing while the count passes through; `dirs` sets scan order where a solver needs a non-default tie-break order.
- **`_row_segment(passable_left, passable_right, c, cols)`** — wall/fog-bounded segment for `$`/`0`/`^`.
- **`_word_motion_chain(step_fn, key, start, max_n, landable, base=1)`** — count-N word motions (`Nw`/`NW`/`Nge`…), chaining a per-level `_w`/`_W`/`_ge` step; `base=2` for two-key prefixes (`ge`/`gE`).
- **Invariant**: refactors here must keep par + answer **byte-identical** across all levels/seeds (capture par/answer/budget before & after, diff) AND pass `vimny/tools/par_audit.py`. The per-level `_w/_b/_e/_W/_B/_E` etc. stay bespoke (their boundary rules differ per level). The analytic solvers (`_par_goblin_gauntlet`, `_par_wardens_keep`) and bespoke-motion ones (`%`, `H/M/L`, `/search`, sentence) are not on the toolkit.

## Mixed vocab token rules
`vimny/art/_gen_runes.py` is the source of truth. Rules for mixed tokens:
- **Decorative endpoints** (glyph appended to a complete word) are the preferred style — thematic connection beats visual match at endpoints.
- **Letter substitution** (glyph replaces a letter mid-word) requires visual or strong thematic justification. `†`=t is very lenient (cross shape). `♝`=l is acceptable (tall narrow bishop ≈ tall letter). Wide glyphs (suits, most chess pieces) mid-word without justification are banned.
- **Double-letter rule**: if substituting a letter that appears doubled (tt, ll), substitute both — e.g. `http` → `h††p`, not `ht†p`. Pure decorative endpoints are exempt.
- **Wide glyphs at endpoints** are fine; wide glyphs mid-word create poor aesthetics and need strong justification.
- Do not add tokens to the txt files directly; run `python3 vimny/art/_gen_runes.py` to regenerate.

## Architecture rules
- **Level identity is the immutable `slug`** (no integer id). `display` is a cosmetic number. `build_dungeon_<slug>`, `tests/test_<slug>.py`, `_par_<slug>`, `_<SLUG>_*` constants, save-progress keys, scroll `level_slug`, and wizard `introduces_slug` all key by slug. **Renumber** = edit `display` / reorder `LEVELS` (never touch a slug) + rerun `vimny/content/_gen_curriculum_table.py` (which regenerates the README's level + command tables).
- Renderer never mutates state (required for future web port).
- **Entity glyph layer — ONE source of truth (`vimny/engine/world.py`).** What letter an entity paints (the char the renderer draws ON TOP of the text/terrain) is defined once in `entity_letter(ent)` (`_ENTITY_LETTER` table + the goblin `echo`→`W`/plain→`g` rule). Every *targeting* command consumes it: `render._ent_cell_str` (the letter-kinds), `motion._cell_char` (f/F/t/T), `search._line_string` (/?*# when `room.search_glyph_entities`). The entity glyph wins over a char-run beneath it (an entity on text is still findable — the wardenverse). **NOTHING in fog is searchable:** `search._match_positions` skips any match whose START cell is in `room.fog_cells` (a search jump lands the cursor ON the match start, and fog is impassable), and the `_line_string` entity overlay skips fogged entities — the renderer draws blank stone there, and what you cannot see you cannot search. Line jumps already skip fog for free (`_first_non_blank_col` only considers `is_passable` cells), so fogging a region seals it against `/`, `*`, `H`/`M`/`L`, `G`/`gg`, walking and word motions all at once — the Warden Manifold uses this three ways (the whole grand hall until the brazier ritual, each podium niche until its round's stagger, the treasure pocket until the seal). That is also what lets it turn `room.search_glyph_entities` on without minting a teleport leak: `/W` is dead until the tick parts his fog, then jumps the player straight onto the revealed Warden for the strike (`x` strikes at one's own cell). RE-laying fog needs a player-position guard — fog is impassable, so never fog a cell the player stands on (the Manifold's R2 re-corruption re-fogs the niche only when the player is outside it). Ward/door conditions over glyphs in a foggable region must read the CELL TYPE, not `is_passable` (fog made the Manifold's ward-words "not on the floor" and ward 1 read broken at entry). `entity_letter` is `None` for decorative kinds (doors/keys/chests/exits/shields) → they're not text-matchable and `_cell_char` falls through to the char/terrain. Cursor-stop semantics for `^`/first-non-blank use `CARET_TRANSPARENT` (floor-like markers passed through; foes/loot are content). **Never re-hardcode an entity→glyph map in a consumer** — add the kind to `entity_letter`/`CARET_TRANSPARENT` and all commands stay in lockstep (anti-drift test: `tests/test_entity_glyph_layer.py`). (The register-preview map `render._REG_ENTITY` is a separate display layer, not a targeting source.)
- **Linewise ops land on the FIRST NON-BLANK (Vim-true, 2026-07-12).** `operator._cursor_to_line_start` (dd, `>>`/`<<`, linewise V-ops, case doubles) parks on `_first_non_blank_col` — the first CHARACTER, falling back to the leftmost passable cell on a bare row. Levels whose bays start with blank floor before their words rely on this (the Selection Halls' post-V cursor = the word = the shaft anchor); the Operator's Vault oubliettes still work (bare pocket rows have no glyphs → fallback). Its old first-passable landing was the pre-2026-07-12 behavior; the vault's C10 tape got one key cheaper (par 93→92).
- **Visual ops in the main loop**: `d y c x ~ < > U u` (U/u = the case SETS gU/gu — with a live selection `u` is NOT undo), gated on `visual_op` except the `x` freebie; multi-row charwise d/c/y/case use PER-ROW bounds (`_apply_charwise_multi` + the case twin — never linewise-collapse a charwise selection); block d/c close each row's gap independently; block `I`/`A`/`c` typed text replays into every selected row on Esc (`block_ins` state in `run_dungeon` — one undo snapshot covers the whole block edit; the replay spends nothing and stays off the karaoke tape). `<C-v>` (`\x16`) shows on answer tapes as the two glyphs `<C-v>` and the tracker consumes both for the one keystroke — it is LOAD-BEARING, so unlike Esc it must be visible (playtest 2026-07-12: an omitted `<C-v>` made the tape unplayable — `d`+`2j` read as a linewise delete). Visual ops call `_content_ticks()` so gates open on the strike itself. `.` after any INSERT-family change replays the recorded text + the implicit Esc (`insert_typed` attached to `last_change`; dot of a visual op is still a silent no-op — no dispatch branch).
- **Paragraph jumps (`{`/`}`) never vault walls**: the target is Vim's (the first blank row — passable, character-free — in the direction) but the landing is `_segment_left` of the player's OWN column on that row, or NO MOVE. No leftmost-cell or extreme-row fallback (those teleported players sideways through walls into sealed pockets/treasure rooms), and no scanning past a blocked blank row (that would mint long-range wormholes). See `tests/test_operators_vault.py::test_paragraph_jumps_respect_the_walls`.
- **Word classes are Vim's, with ONE source of truth: `engine.motion._is_word_char`** (default 'iskeyword' + utf_class, verified against `vim -u NONE`). The crucial fact: vim's `{0x20a0, 0x27ff}` "all kinds of symbols" range makes EVERY game symbol (suits, planets, dice, †, ⌘, math) PUNCTUATION — `w`/`b`/`e` stop on them, an adjacent symbol run is one punctuation word, `W`/`B`/`E` take whole tokens. Par solvers and `vimny/art/_gen_runes.py` must use the engine function, never a local copy (two solver copies drifted once — that's how the So-as-word-char bug shipped).
- **`D`/`C` shorthands are gated as their own lessons**: the parser tags them (`action['shorthand'] = 'D'/'C'`) and `command_guard` requires that token in `known_commands` on top of the operator + `'$'`. The Operator's Vault (L18) forces the two-key `d$` grammar; `D` unlocks at the Cipher Cell (L19), `C` at the Change Extension (display 24 — split off from the Change Annex, which teaches `c{m}`/`cc`/`s`).
- **Hint bar wraps to a 2nd row when the cheat sheet is long (`vimny/render/renderer._wrap_cheatsheet`).** `hint_text` is computed EARLY (before `game_h`), wrapped into up to 2 rows breaking only at command boundaries (the double space between `keys:desc` entries, never mid-command); each extra hint row is subtracted from `game_h` (`term.height - 8 - (len(hint_lines)-1)`) so the box height still equals the terminal. On a full-width terminal (iw up to 187) two rows show even the longest boss bar in full; on a narrow 80-col terminal a 366-char act bar still exceeds 2×78 and the 2nd row ellipsizes. Boss bars list the WHOLE act they cap (`act_commands(slug)`), so they are the long ones. Frame-height invariant + wrap behaviour pinned in `tests/test_hint_bar.py`.
- **Gating ↔ hint-bar parity — ONE gate per lesson, or declare the family in one place.** `action_allowed` (gating, the source of truth for "usable") and the hint bar (display, tiers from `known_commands` diffs) are independent paths that can drift, producing **unlocked-but-invisible** keys. Two rules keep them in lockstep: (1) **a key that is its own lesson gets its own gate token** so the gating boundary == the curriculum tier == what the bar shows — e.g. insert: `i`/`a` gate on `insert` (Inscription Halls) but `o`/`O`/`I`/`A` gate on their OWN tokens (Sculpting Chambers, display 24), via the `variant`-aware branch in `command_guard`; never let one token gate keys taught at different levels. (2) **when one token legitimately unlocks a whole family** (`/`→`? n N`, `mark`→`` `{a} `` `'{a}`, `subst`→`:%s//g :g/pat/d &`), declare the siblings in `vimny/render/hint_bar.py` `_FAMILY` OR bundle them into one `keys` cell in `vim_commands.md` (`d{m}  dd`, `y{m}  yy`, `c{m}  cc`) — the bar only shows what a tier's tokens resolve to. The anti-drift guard is `tests/test_hint_bar.py::test_bar_shows_every_newly_unlocked_command`: for every level, every command `action_allowed` NEWLY permits must appear on that level's bar (and the converse — a deferred key must be neither usable nor shown early). Add a new gated command's `(keystrokes, 'keys:desc')` row to `_GATED` and the parity is enforced.
- **Saddle registers ride with the horse (`command_guard.is_saddle_register`).** The post-adoption register wing (`docs/blueprints/registry_wing.md`) frames the horse's saddle as the register store, so the *saddle* registers — every register named by a **digit or symbol** (`"0`–`"9` `"-` `"_` `"/` `":` `".` `"%` `"#` `"=` `"*` `"+`) — are gated on the horse being in the room. `action_allowed(action, known, edit_mode, horse_present=)` returns False for a saddle register when `horse_present` is False; `run_dungeon` wraps the pure guard (`_action_allowed`/`_guard_message`) with the live `_horse_here()` state, so these registers are dead on boss levels, combat crushes and the whole pre-adoption game. **Exempt** (their own gates, no horse needed): the unnamed register `""` (token `register`) and the named / macro registers `"a`–`"z` / `"A`–`"Z` (token `reg_named`, the `q`/`@` machinery — `.isalpha()` is the test). Guard is `tests/test_horse_egg.py::test_saddle_registers_ride_with_the_horse`.
- **The numbered delete ring (`registers._push_ring`, 2026-08-12).** A **linewise** delete shifts `"1`→`"2`→…→`"9` and stores the new clip in `"1`; the tenth-oldest falls off the end. It lives in `write_register` because every delete in the game funnels through there (eleven call sites in `game.py`, two in `substitute.py`), so there is exactly one place the ring can be pushed and no way for a new delete path to forget. Four things deliberately do **not** push it: a yank (`is_delete=False`), a **charwise** delete (that is `"-`'s job — The Small Cut, not yet built; until then small cuts leave the ring alone, which is the vim-true half), a black-hole `"_dd` (returns before the push, as in vim), and a macro recording. A *named* delete (`"add`) **does** push — the ring records what was thrown away, not which register you aimed at — and that is the whole reason `"1p` can retrieve a cut the unnamed register lost three deletes ago. `"0` is **not** part of the ring: it is the last *yank*, untouched by any delete, which is the other half of the lesson. Gate token is `reg_numbered`, **split out of `reg_named`** by `command_guard._register_token` — everyone who reaches the registry wing already holds `reg_named`, so folding the digits into it would hand out the ring before the level that teaches it. The remaining symbol registers keep `reg_named` plus the horse gate until their own levels ship. Guards: `tests/test_register_ring.py`.
- **A macro IS a register (unified 2026-07-25, user-directed).** There is no separate macro store — `player.macros` is gone. `q{reg}` records through `registers.record_register` into the *text* register of the same name, so `qa` clobbers whatever `"a` held; `@{reg}` reads the register back through `registers.clip_to_keys`, so **any** register replays as keystrokes, including text you merely yanked off the floor. This is vim's actual model and the reason `q`/`@` take register names at all. Two details worth knowing: recording deliberately does **not** touch `""` or `"0` (vim leaves them alone while recording), which is why `record_register` exists alongside `write_register`; and `qA` appends to `"a` via the same `_append_clip` as `"A`. Control characters are stored in **caret notation** (`^[` for Esc) — vim keeps the raw byte and merely draws it that way, but storing the drawn form means a macro register can be pasted into a buffer and read on screen without a raw escape byte ever reaching the terminal, and `clip_to_keys` decodes it back for `@`. Levels whose answer tapes record a macro must pick a recording register that does not collide with text they are holding (the Register II tape records into `qq` precisely because `"a`/`"b` are full). Guards: `tests/test_macro.py::TestMacrosAreRegisters` and `test_register_named_vault.py::test_recording_into_a_clobbers_the_word_stored_there`.
- `Budget.spend(cost)` where `cost = 1` (single step) or `len(str(n))+1` (count-n move).
- `apply_motion` loops step-by-step; void rune check fires only on final cell (intentional — Vim-faithful).
- Undo stack entries are either `(row, col, spent)` tuples (movement) or dicts with `entities`/`fog_col` keys (door-open).
- **`u` UNDOES MOTIONS, AND THAT IS THE ONE DELIBERATE BREAK WITH VIM IN THE MOVEMENT KEYS.** Vim's undo is for CHANGES: it will not walk the cursor back from a `4j`. Vimny pushes movement onto `undo_stack` too (`vimny/game.py`'s motion branch appends `prev_pos`), and `_pop_history_step` restores `player.row/col` **and `budget.spent`** — so a wrong turn costs nothing once taken back. The reason is the budget: a game that charges for every keypress must let a player walk a route they are not sure about, or exploring a room becomes something you pay for and learners stop trying things. It is also the only refund in the game, which is why the mistake-and-undo beat in the README's demo GIF lands on the same keystroke count it started from. Everything `u` does to EDITS is Vim's behaviour, snapshot stack and all. Two consequences worth remembering: a mistake that does not actually MOVE pushes nothing, so the next `u` eats the previous good motion instead (this is why a promo tape's "wrong jump" has to be a jump that lands somewhere); and undoing while carrying a key drops it where you stood, which is a deliberate precision tax, not a bug.

- **Terminology — "character"/"CharRun", not "rune".** On-screen characters are `CharRun` objects (`room.char_runs`); in code, comments, and docstrings call them **characters** / **character runs**. Clips key the list under `'char_runs'`; the merge helper is `_merge_adjacent_char_runs`. "rune" is reserved for the THEME only: level names (The Rune Halls, The Runic Archives), the vocab pipeline (`vimny/art/_gen_runes.py`, `vocab_*.txt`), wizard poems, and `<kind> rune` type phrases (e.g. "void rune"). Do not use "rune" to mean a generic character or "rune cluster" to mean a word. **Likewise "room", not "chamber" or "hall", for one segment of a multi-room level** — a CHAMBER is part of one map, joined to the rest of it by a hallway or a door and reachable without leaving the grid (what `_hall_of_echoes_tick` calls its segments); a ROOM is its own grid, which is what `dungeon.rooms` holds. *Halls* is the name of six levels, so it was never available. See the DESCENT bullet below.
- **Reflow grid (Vim line model), NOT an overlay grid:** editing flows like a real Vim line — insert/`x`/`d`/`s`/paste SHIFT content within the wall-bounded row (blanks are spaces, so a word past a gap is still pushed). Content shoved past a FIXED brink (any wall or void rune) is lost over the brink; water is movable and a wave sweeps any entity it reaches into the void (drown). **A mid-row wall (or void rune) BOUNDS the reflow in BOTH directions** — push (`open_gap`) and pull (`close_gap`) are symmetric: each brink-bounded stretch flows as its own line, the glyph shoved against the wall falls INTO it, and content on the FAR side of the wall is untouched. So a read-only clue/plaque set behind a wall is safe from an edit on the other side, on EITHER side of it. **The symmetry is over BRINKS only — over ENTITIES the two are deliberately asymmetric:** the pull is permeable (text slides past a door or a creature — The Operator's Vault's par path relies on it) while the push loses a glyph shoved onto an entity. `remove_row` additionally refuses any row holding a live `edit_immune` entity (`vimny/engine/reflow.py`), which is how a boss's row resists a join and how an `edit_immune` exit is made join-proof; the same immunity is honoured by `vimny/engine/operator.py`, `vimny/engine/visual.py` and `vimny/engine/substitute.py`. Note the guard is `alive and edit_immune`, so a dead immune entity stops protecting its row. `r`/`R` overwrite in place (correct Vim) and do not reflow. Charwise paste: `p` inserts after the cursor, `P` before; the cursor lands on the last pasted cell (including a creature — the `x`-attack position). Pasting a key onto a locked door unlocks it and steps the player onto the door (consistent with paste). Reflow is universal — `is_ledge` always True. Hold any new editing command to this model. See `vimny/engine/reflow.py`.
- **Pinned kinds never recolor:** `normalize_row_word_kinds` (vimny/engine/world.py) repaints adjacent clusters to the leftmost cluster's kind so a WORD renders in one color — but kinds in `_PINNED_KINDS` (`void`, `flame`, `pedestal`) are mechanic-bearing identities, skipped both as leaders and as targets. A flame pasted against text must stay `flame` (it drives the renderer's flicker) and shoved `…` embers must stay `pedestal` (or the Beacon Tiers tick's stray-sweep misses them — the bug that motivated the rule). Add any future rule-carrying kind to `_PINNED_KINDS`, not special cases downstream.
- **THE STONE LAW is enforced, not requested (`vimny/engine/motion.enforce_fog_law`).** Every foggable cell the eye cannot reach from spawn (walls-only `_vision_flood`) starts fogged, and this is applied centrally — `main._build_dungeon` holds every room of every shipped level to it, `format.build` does the same for downloaded ones — so fog is DERIVED from the walls rather than remembered beside them. It was opt-in until 2026-07-27 (each builder calling `apply_stone_fog` for itself) and drifted exactly as you would expect: the Grandmaster's arena grew a sealed pocket after its fog was laid, and shipped with 52 lit cells behind the seal, the exit among them. The law is a FLOOR — scripted fog is a superset and about a third of the game lays more, but no room may lay less, and `tests/test_fog_law.py` asserts that over every room of every level. `auto_fog` (whether the fog re-reveals as sight crosses an opened door) is left alone by the enforcement, because holding the reveal back is a design decision: the Manifold and Scrivener re-lay their fog each turn and must not have it lifted. A room that had NO fog is opted into auto-reveal, which is what every hand-written call already chose. (Since wave 1 closed, every shipped level chooses it: the 2026-08-22 conversion moved the last 21 stragglers — builders that predated the law or laid fog through non-auto helpers — onto `build`'s always-reveal. A buffer is read, not explored.

It is deliberately not in the file format — an author-supplied banner is a text channel into other players' screens — so a shipped level rebuilt from its own file would fall back to the generic wording. That is the one thing phase 6 of the port still has to answer for.

- **A TAPE MAY NAME A WORD IT CANNOT SPELL (`engine.tape.SLOT_REF`, `room.fill_slots`).** A `fill` grows different words for every player, so a route that TYPES one of them — which is most of the change/insert curriculum — could not be written down: `cerune<Esc>` solves the author's roll and nobody else's. That is why the shipped word levels GENERATE their answer tape from the seed, and why they could not be level files. A tape may now say `<fill0.3>` — *the word fill 0 grew in slot 3*, both indices 0-based to match `fill[0]` in every error message the format prints. `format.build` records what each fill laid (`room.fill_slots`, one list per directive, in laying order) and resolves the tape once, into `room.answer`, so the karaoke sheet, the replayer and the cost model all still see ordinary letters and know nothing about slots. The tape AS WRITTEN is kept on `room.answer_source` so `from_room` writes the reference back out rather than pinning the level to one roll. **Two laws keep par a single number**, both enforced in `validate._check_slot_refs`: a fill a tape reads from must grow words of ONE length (typing a 6-letter word costs 3 keys more than a 3-letter one — `tests/test_fill_slots.py` pins 9/10/12), and a saying pool cannot be read at all, since which proverb turned up decides the length too. The single-length law does a **second** job nobody asked it for: word length is what decides where the next word starts, so a fixed-length fill lays words in exactly the same places, and in the same number, for every player — only the letters are re-rolled (pinned by `test_a_fixed_length_fill_lays_the_SAME_WALL_for_every_player`). That is why a COUNTED motion needs no notation of its own: `3e` vs `4e` is decidable once, at authoring time, from the author's own build. The corresponding limit, worth stating plainly rather than papering over: a level whose ROUTE is meant to vary with the roll cannot be scored at all, because par is one number. Authors find the slot with `engine.editor.slot_at` behind the forge's `:fill?` — standing on a word reports `<fill0.7>`, or refuses when the fill rolls its lengths; counting to slot 23 by eye is a chore with a wrong answer at the end of it. The trap to remember: **every replay must take the tape the BUILD resolved, never `lvl.solution`** — feeding `<fill0.0>` to the game plays it as ten keypresses (`f` finds a character, `0` jumps to the margin) and reports a par for a route nobody could play. Both replays in `validate` were fixed to pass `dungeon.room.answer` when this landed.
- **A LEVEL IS A DESCENT, NOT A MAP (`sharing.format.Room`, `Level.then`, `main._room_door`).** Rooms are walked in order, each one's exit is the next one's door, and there is no going back — the shape both multi-room shipped levels already had in code, now sayable in a file. A room GRAPH would need doors that name rooms, a way to say which door you came in by, and a spawn per door; nothing anybody has wanted to write needs it. **The noun is ROOM.** A *chamber* is part of one map, joined to the rest of it by a hallway or a door and walkable to without leaving the grid — what `main._hall_of_echoes_tick` means by it. These are separate grids, and separate grids are exactly what `dungeon.rooms` has always held, so "room" is the engine's own word for them. (*Hall* was never available: six shipped levels are named Halls and one is a slug.) The cost is that `vimny/sharing/format.py` has two Rooms in it — `format.Room` is a room AS WRITTEN (geometry and content, inert) and the engine's live buffer class is imported there as `LiveRoom`; `build` turns each of the first into one of the second. The first room is the level's own `geometry` and content keys, so a one-room level is untouched in the file and in the build; the rest are **`then`** — named that, and not `rooms[1:]`, because an author who writes `then[0]` should get the room AFTER the first, and a list whose zeroth entry is the second room is a trap on the first line. `Level.rooms` is a **projection** (the level's own fields as room 0, then `then`), so there is no second copy of room 0 to keep in step, and everything downstream — build, crop, bounds, standability, determinism, the golf lower bound — loops over it. Consequences worth knowing: **fills are numbered across the level in room order** (`<fill4.0>` is the level's fifth fill wherever it stands; `room.fill_index0` is how `slot_at` reports a room's own fills in the level's numbering); **the tape belongs to the level, not a room** — one route walks them all, so it is resolved once onto room 0 and the karaoke position travels through the doors with the player; **par is the whole descent**, and the golf lower bound is the sum of the per-room walks. The door is asked at the WIN CHECK (`_room_door`), not in the per-turn ticks: a room's exit is reached and the level ends in the same instant, so a rule that ran a moment later would be answering a level that had already been won. A shut seal on the exit cell is what makes a door conditional — you cannot stand on stone, so there is no second condition. `format.capture_room` captures a live room as a room-as-written, which is how the round-trip probe (and a builder port) takes a multi-room dungeon a room at a time; **`from_room` captures ONE room and a caller that forgets to pass `then` saves a two-room level as a one-room one** (`draft.sync` passes it; `tests/test_rooms.py` pins it). The forge builds them one at a time: `draft.room_index` is the one on screen and `:room` moves between them (see Open work).
- **THE PORT GAP IS A NUMBER, not an impression (`tests/test_round_trip.py`).** There are two materialisers — `main._build_dungeon` (a hand-written builder per shipped slug) and `vimny/sharing/format.build` (a level file) — and the long-run intent is that there is one, so the forge is complete by construction rather than by assurance. The test pushes every shipped level through `from_room → dumps → loads → build` and diffs it against what went in (cells, spawn, exit, runs, entities, mist, fog, veiled, wrap, seals, room count). Whatever differs must be written down in `KNOWN_GAPS`, by slug, with a reason. **56 of 60 survive the trip whole** as of 2026-08-23 (43 on 2026-08-01). It fails in BOTH directions: an unlisted loss is a regression, and a listed loss that no longer happens is a stale exemption — i.e. an audit passing vacuously — so landing a phase of the port means deleting lines from that table in the same commit. The probe walks EVERY room of a dungeon, not just the one the player starts in — a probe that read room 0 alone would report a two-room level as whole while leaving half of it behind. The four standing gaps, each working as designed rather than waiting to be fixed: **the Sanctum HEALED 2026-08-23** (build() gives the exit marker entity to the LAST room alone — a transit room's door is its position, `_room_door` asks the position); **underwater-off-the-water HEALED 2026-08-23** (the format learned an `underwater` coordinate list beside inline `M` — the layer was called `mist` until this date and files under the old name still load — and shelving_room/refrain_vault ride it; the Shelving POCKET rides the water too (sunken until the tick unveils it), so that level healed outright); **waypoint_sanctum** keeps its scripted plugh fog as a deliberate pin — the darkness is an EVENT (it lifts when the ? leg lands in pocket 1), files have no events by doctrine, a static `fog:` key would break the derived-fog invariant, and no named-layer move fits text that must become searchable mid-play; **the Wardenverse** is a room with no exit, left by an event rather than a door; **the Archivist's Library** is the agreed exception (a wrap buffer whose text IS the level, its exit a reading position); **the dummy's horse** is a session entity `from_room` drops on purpose (`_TRANSIENT_KINDS`).
- **Fog hides text from search, uniformly.** A fogged word is unfindable by every search — `/ ? n N * #` alike (`vimny/engine/search.py`). Levels use this deliberately: a decoy twin under scripted fog cannot be reached by searching for it. Because it is uniform, there is no search that sees through sunken ground, so a level may rely on it without carving an exception.
- **Underwater bounds line-scoped scans; teleports do not cross it.** Water is transparent — text on the far shore is legible — but water lying over the channel stops every line-scoped scan at the bank: `$`/`0`/`^` via `_cross_water`'s fog check, and `f`/`F`/`t`/`T` by the same blocker set. Teleports (`G`/`H`/`M`/`L`/`{n}G`) are unaffected and land on the row's first standable cell, i.e. the NEAR shore. This is the pairing that makes "readable but unreachable" work.
- **Underwater instead of stone — the readability-without-reachability pattern.** Where a level needs a barrier the player can see *through* but not walk through, build it from misted water rather than wall: everything stays visible, while feet are blocked by the water, line scans by the mist, and `{`/`}` skip flooded rows exactly as they skip walls. Used for the Waterworks pocket ring, sanctum seals and vault boxes. A pattern, not a rule — reach for it when visibility is the point.
- **THE LANDING RULE (engine-wide): a cell the cursor cannot stand on is not a landing.** Every text-targeting jump filters destinations by `is_passable`: line jumps (`_first_non_blank_col`), `f/F/t/T` (`_apply_find`), search (`_match_positions` skips matches starting on impassable cells — fog, walls, water alike), sentence jumps (`(`/`)` filter `_sentence_starts_all`), and the word-motion family (`w/b/e/W/B/E/ge/gE` revert if the final landing is impassable — their scan helpers stop at walls but the IN-WORD edge moves walk the run itself, and a run may straddle floor and wall, e.g. a plaque crossing a promenade gap). Text set in walls (plaque bands) is therefore visible but never a jump target. ONE deliberate exception: `$`/`0`/`^` use `_cross_water` and may land ON WATER — the main loop's drown trap (damage + bounce) punishes it; that is a designed hazard, not a leak. The Inscription Halls shipped a `)`-cheese (buffer-wide sentence hop straight past its bank gates, even into walls) before this rule existed — when adding any new jump motion, filter its landings, and pressure-test new levels with a motion sweep (`test_inscription_halls.py::test_every_known_motion_lands_passable_and_west` is the template).
- **Teleport audit for every new level:** `G`/`{n}G`/`gg`/`H`/`M`/`L` (known since the Lineheads / Screen Vault) TELEPORT to a row's first non-blank (`_first_non_blank_col`: first character, else leftmost passable cell), scanning past all-wall rows. Any passable row is a landing site regardless of walls in between — a gated area with its own row is reachable by jump. Audit WALKING approaches from every adjacent row too (the Beacon Tiers' first exit row was walkable from above, east of its seal). Design every level so jumps land on the gated SIDE of its doors (the Beacon Tiers keeps the exit in a one-cell pocket behind the seal: jumps land on the beacon row's first non-blank — always a brazier glyph, the exit being CARET_TRANSPARENT — and no other row touches the pocket), or make the landing lethal (the Screen Vault's void row). Pin it with a landing test (`test_quartermaster.py::test_line_jumps_never_land_in_the_pocket`). **Since `A`/`o`/`O` (the Sculpting Chambers), the audit has a THIRD front — FABRICATED floor:** `A` carves new floor east of any standable cell and `o`/`O` open fresh rows, so "plain floor behind walls" is reachable by building toward it (the 2026-07-12 carve bypass won the Overwrite Halls in 13 keys); geometry alone cannot contain it, because fabricated rows carry none of your runes/walls. A gated exit must therefore be STONE until its win-condition holds (the FINAL SEAL — a `Seal` whose `requires` names every bolt, so the exit floors only when every plaque reads true; same diegesis as the sculpting vault door, and the renderer draws a sealed exit as plain stone). Levels with row-editing verbs (`J`, `dd`) additionally: anchor tick coordinates to `room.exit_pos` (which `_shift_rows` keeps true), keep the gate row join-proof via an `edit_immune` exit entity, and run the jump audit in every INTERMEDIATE geometry along the canonical route, not just as-built (`test_joiners_gate.py`).
- **Void runes are TEXT, not just terrain:** a `○` is a `CharRun` (kind=`void`) — `/`/`*` search it, `x` deletes it, and `:s` substitutes it. Substituting a void away fills the hole as ordinary text (replacement chars take the line's first non-void kind); an untouched void keeps kind=`void`. The reflow FIXED-brink rule (content shoved into a void falls off) governs only the push/pull editing ops (`i`/`x`/`d`/`p`), NOT the whole-line rewrite of `:s`. Anything drawn with a glyph (words, void runes) is text to `/`/`x`/`:s`; cell-terrain with no glyph (walls, water) is invisible to all three. See `vimny/engine/substitute.py` / `vimny/engine/search.py`.
- **Ex substitute & global (`vimny/engine/substitute.py`):** `:s`/`:g`/`:v`/`&`/`g&`, taught at The Spellwright's Forge (token `subst`). A "line" is a row's wall-bounded glyphs with gaps as spaces (`_read_line` → text + per-char kinds); `set_line_text` re-lays the row (content past the right wall falls off). Ranges (`%` `N` `.` `$` `'a` `'<'>` `±N` `a,b`/`a;b`; `:g` defaults to whole file), `:s` flags `g c i I n e &` + count, full Vim replacement (`& \0-\9 ~ \u\U\l\L\E \r \t`), and the repeats all there. `&`/`g&` parse to a `sub_repeat` action.
- **Vertical / ledge reflow (BUILT, `vimny/engine/reflow.py`):** three primitives, all there. `_insert_blank_row` = vertical add (`o`/`O`, and linewise `p`/`P` which now insert REAL rows and shift the map down). `remove_row` = vertical collapse (`dd` and visual-line `d`, the exact inverse of `o`; `cc`/`S`/`D`/`C` still clear in place). A REFUSED collapse (edit-immune occupant on the row — gates/bosses parry; or a one-row buffer — the dungeon can't reach zero lines) must be a free no-op: no budget, no register write, no undo entry, no `last_change`, and a "parried"/"last line resists" message — never a silent false `Deleted.` (regression: `test_operators_vault.py::test_blocked_dd_*`). `extend_floor`/`carve_floor` = horizontal ledge-build (`A` jumps to the line END — just past the cursor's SEGMENT edge, the same wall-bounded boundary `$`/`0` honour (2026-07-12: row-global rightmost was a leak — `A` vaulted shut gate bolts and landed in the far wall), skipping trailing floor as Vim skips trailing spaces, NOT just past the last character — then lays new floor into the void one plank per keystroke, DOUBLING `room.cols` at the right border up to `_MAX_COLS`=200 — the **edge of the world**, past which `A`/`J` refuse and show `_EDGE_OF_WORLD_MSG`; a `○` void rune also stops it, via `room._last_build_blocked`). `A` is the ONLY floor-creating command — interior insert AND `>>` shove the tail off the right brink (`>>` reflows via `open_gap`; it does NOT clamp at the wall). `J`/`gJ` (join, The Joiner's Gate) = `remove_row(row+1)` + `extend_floor`-append onto this line (`J` one space at the seam + cursor there, `gJ` none; `nJ` joins n lines; preserves the joined line's internal spacing). Undo snapshots `rows`+`cols`+`cells`; pass `player` to `remove_row`/`_insert_blank_row` so marks/jumplist shift with the rows. **`split_line_down` = insert-mode `<Enter>`, the BOUNDED vertical split (the vertical mirror of `open_gap`, NOT `o`): the head (glyphs left of the cursor) stays, the tail (glyphs at/after the cursor) drops to the row BELOW re-aligned to that row's column 0 (its first floor cell — Vim-faithful), and every row beneath shifts straight DOWN one row, same columns. The dungeon NEVER grows height — so a glyph pushed onto a wall / void rune / entity, or off the bottom, falls into the void (`room._last_void_falls`); walls/runes/entities stay FIXED. The cursor parks at the new line's column 0. Because the whole insert session is one undo, the split needs no extra snapshot. Wired in `vimny/game.py`'s INSERT player block on `KEY_ENTER`/`\n`/`\r`, costing 1 budget; the confirmed `fist|gate` case — splitting onto a narrow throat keeps only the spine glyph and spills the rest.
- **Scrolls, blessings & the Codex — three catalogues, one library + one fold-book.** Found/dropped scrolls live in `vimny/content/scrolls.py` (`SCROLL_CATALOG`, relic ids in `RELIC_SCROLL_IDS`); wizard **blessings** (every poem in `vimny/art/wizard_wisdom.txt`) live in `vimny/content/blessings.py` (`BLESSING_CATALOG`, id = `blessing_<slugified-name>`, **case-preserved** so `w b e`/`W B E` don't collide; all-punctuation names fall back to the introduced slug). Discovery state: scrolls in `progress['extras']`, read-marks in `progress['scrolls_seen']`, blessings in `progress['blessings_seen']`. A blessing is recorded seen the moment the wizard recites it — `_record_blessing_seen(progress, name, ...)` fires at each `run_wizard_blessing` call site in `vimny/game.py` (home-row, next-lesson via `title.next_lesson_quote_entry`, final blessing). **Both surfaces render the same three groups — codex / relics / blessings:** (1) the scroll library (`vimny/render/scroll_library.py` `library_rows` — one `subtree_lines` per group, each scroll row tagged `group`; blessing rows gate on `blessings_seen`, scroll rows on `extras`); (2) the Codex `:h` pane (`vimny/engine/codex.py`), built via `CodexPane(groups=[('codex', secs), …])`. `_show_scroll_by_id` routes a `blessing_*` id to `blessing_scroll_content` (poem as centred amber verse). **`CodexPane` supports nested folds:** a line is hidden iff any *closed* fold strictly encloses it (`start < line < end`), so a closed group hides its section headers — `_header_at`/`_enclosing` drive toggle/search/jump/render, ridges indent by `depth`. The flat `CodexPane(sections)` path (depth-0 folds) is unchanged.
- **Netrw navigation is ONE shared engine — `NetrwNav` (`vimny/game.py`).** Every read-only cursor-over-lines screen — the overworld (`run_overworld`), the scroll library (`run_scroll_library`), and the colours palette (`run_colors`) — drives the same `NetrwNav` instance, so `gg`/`G`/`{n}G`, `H`/`M`/`L`, `{`/`}`, `w`/`b`/`e`/`W`/`B`/`E`, `f`/`F`/`t`/`T` + `;`/`,`, `*`/`#`, marks (`m{a}`/`` `{a} ``/`'{a}`/`''`), the Ctrl-o/i jump list, Ctrl-d/u/f/b paging, counts, curswant columns (`0`/`^`/`$`/`h`/`l`), and the `/`/`?` search + `:` command line all behave identically and are fixed in one place. The host supplies buffer-specific callables — `get_lines()`, `label(ln)` (motion/search text), `section_key(ln)` (`{`/`}` grouping), `gate(tok, label)` (learned-command gating → sets `player.error`; the admin-only colours screen passes `lambda t,l: True`), `avail()` (viewport height) — plus a `marks` dict and `:`-completions. `feed(key)` returns `None` (consumed), `('cmd', text)` (a `:` command for the host), or `('key', raw, key)` (a key the engine doesn't own — Enter, D, R, -, Esc — for the host to dispatch). The host keeps `nav.scroll_offset` in sync by writing back whatever its renderer computes each frame; marks are session-scoped on the player (`player.ow_marks` / `player.scroll_marks` / `player.color_marks`). Each host renderer (`vimny/render/overworld.py`, `vimny/render/scroll_library.py`, `vimny/render/color_palette.py`) exposes a structural row list + `row_label`/`row_section_key` and a viewport renderer that takes `cursor`/`scroll_offset`/`cmd_prefix` and returns the adjusted offset. String motions (`_owm_w`/`_owm_b`/`_owm_e`/`_owm_find`/`_owm_word_at`) and `_section_starts` are the shared primitives; `main._ow_section`/`_ow_section_key` stay for the overworld's grouping. Anti-drift: `tests/test_netrw_nav.py` proves the engine directly (over the overworld AND colours buffers); `tests/test_overworld_search.py` proves the overworld host still behaves identically. Add a new netrw motion once, in `NetrwNav`, and every screen gets it.
- **Overworld = a netrw buffer (`vimny/render/overworld.py` + `run_overworld` in `vimny/game.py`):** a flat list of selectable lines — the `"` comment header (lines 1–6, numbered), `../`/`./`, the level entries, then a `custom/` section of saved layouts. The cursor is an index into that list, defaulting to `../` (`default_cursor`); `_scroll_offset` is a stateful Vim-like viewport (no cling). Motions are gated by `_known_from_progress(progress)` (admin bypasses): `j`/`k` always; counts, `gg`/`G`, `{n}G` (line-based, 1-indexed over the buffer), `H`/`M`/`L`, `{`/`}`, and `Ctrl-d`/`u`/`f`/`b` once learned. `:set number`/`relativenumber`/`nonumber` (+ `nu`/`rnu`/`nonu`/`nornu`) toggle the gutter. `R` renames a custom layout (`save_manager.rename_layout`), `D` deletes one (y-confirm); built-ins refuse `D`/`R`, and the buffer is read-only (`d`/`dd` refuse). Live blinking cursor via `term.cvvis`; `_done` restores `term.civis` on exit.

- **Community levels are DATA, never code (`vimny/sharing/`).** A shipped level is a `build_dungeon_<slug>` function; a community level is a declarative JSON file parsed into a `Room` and never executed — the format IS the security boundary, and it is the one decision here that cannot be revisited cheaply. Four rules hold the feature together. (1) **Par is derived, never declared**: `vimny/sharing/replay.py` replays the author's keystroke tape through the real `run_dungeon` with rendering silenced, and `budget.spent` is par; `budget = ceil(par*1.4)` follows. The same replay is the solvability proof, so one artifact does both jobs. It is an upper bound on par, not an optimum — hence "author's par" in the UI. (2) **Fills resolve at build time from the level's own seed** so the file is identical for the author who recorded the tape and every player after; `vimny/sharing/vocab.py` is the single `words()` implementation both the loader and (eventually) the shipped builders call, because a directive that resolved differently for the two is a broken level. (3) **Command scope needs no second implementation**: the replay runs with `run_dungeon(_known=level.known)` — the level's declared `requires + teaches + ALWAYS_ON` — so a tape reaching for an undeclared key is refused by the same `action_allowed` gate the curriculum uses. (4) **Validation runs on LOAD, not only on submission** (`vimny/sharing/library.py`), so a hand-edited file gets the same scrutiny; every rejection names its rule. **Nothing touches the network unbidden** — no phone-home, no telemetry, no update check; `vimny/sharing/library.py` reads `~/.Vimny/levels/` and nothing else, and that must stay true of it. The two things that do reach out are both a command the player typed: `vimny/sharing/remote.py` fetches the shelf's index on `:e remote`, and `vimny/sharing/submit.py` composes a URL for the browser to open on `:submit`. Whatever comes back goes through the same `validate()` a hand-dropped file does, which is what keeps the surface a fetch rather than a trust boundary. Community slugs are namespaced `community/<stem>` so they can never collide with a shipped slug in progress keys. **`python3 -m vimny.sharing audit`** points the same replayer at the shipped curriculum: every par claims a solver found the cheapest route, and a shorter tape falsifies that claim with its own reproduction (it found The Spellwright's Forge's par 45→44 on its first run). A confirmed beat is a solver bug report, not a score. Tape notation writes Esc as `<Esc>` (`vimny/engine/tape.py` — the one source of truth for the alphabet `<Space> <CR> <Esc> <C-v>`), so insert/change routes replay too; Esc spends no budget, which is why adding it to already-par-pinned tapes moved no par. **THE :bar LAW (generalized 2026-08-23):** a command line may chain editor-family statements on `|` (`:1j|1y` and longer) — the head executes this turn and every later statement rides the macro queue as its own `:` line, through the ordinary pipeline. Each `|` replaces what would have been the next statement's colon, so chaining is spend-neutral: there is no pipe-golf. The law covers the editor family only (`s/g/v/&/j/y/m/t/d/</>/&&`); other dialects that read a literal `|` (the forge's `:seal |16` pin flag) pass through verbatim. `vimny/sharing/cli._NO_SINGLE_TAPE` is down to one entry (`grandmasters_sanctum`, two rooms whose arena has no karaoke) and the audit PRINTS skips rather than dropping them, so nothing passes invisibly. **The visibility audit (`tests/test_visibility_audit.py`, 2026-08-23) gives replay EYES**: the par audit and round-trip probe play blind — two shipped sight bugs (the Shelving verses edited invisible, a chest lit behind shut bolts) reached players through exactly that hole. It drives all 59 single-tape levels on their canonical routes with a capturing `render_all` (one call per processed action = one frame), records per-row glyphs plus which cells were hidden (plain fog or veil; ink over underwater ground counts as seen), and diffs consecutive frames: **a row whose text changed must have been fully legible before the change**. Scripted dark-writes get `VISIBILITY_GAPS` with reasons and a stale-exemption tripwire, same contract as KNOWN_GAPS; the four fog-family levels are also watched by name as a fast gate. Always-on at ~12s. An author may declare `alternate: <slug>` to offer a level in place of a shipped one; curriculum position is the invariant, so the validator requires it to teach EXACTLY that slug's `teaches` set AND to `require` nothing a player has not been taught by the time they reach that slug (`known_commands(slug)` minus the slug's own lesson). Nothing consumes the field yet — a valid alternate is not necessarily a better teacher. A level with no `alternate` is a bonus-wing level and carries neither constraint. **`:submit` (`vimny/sharing/submit.py`) is a URL builder, not a client** — it composes GitHub's `new/<branch>?filename=…&value=…` prefill and hands the string to `webbrowser.open` behind an explicit keypress, so Vimny never holds a token, never opens the connection, and the pull request is made by GitHub under the author's own account. That is also why the byline is `:author` and nothing else: a name going into a public repo is the author's to choose, never inferred from the save. The one thing that can degrade is length — a level past `URL_LIMIT` opens the form EMPTY with its file written beside the link in `~/.Vimny/submit/`, which is a step, not a failure. `:submit` shares `:publish`'s gate (forge-only, so admin-only) and refuses anything the validator has not replayed to a win: a pull request is a reviewer's time.
- **The forge: authoring a level in-game (`vimny/sharing/draft.py`, admin-only `forge/` in the overworld).** Two decisions carry it. (1) **A draft IS a `Level`, and the Room is what the Level renders to** — not the other way round, which is how `~/.Vimny/layouts/` works and why layouts can never express a fill: a fill is a directive that grows words at build time, so once you keep the words and throw the directive away, a region an author asked to be "sixty cells of proverbs" is frozen text the next edit cannot regrow. The Level is authoritative for everything declarative (fills, vocabulary, metadata), the Room for everything painted (cells, hand-placed text, entities), and `draft.sync` moves the second into the first. Corollary: a fill REGION is owned by its directive, so `engine.editor.in_fill` refuses edits inside one (`:fill!` bakes it into editable text). Ownership is by region, never by object identity — `_merge_adjacent_char_runs` mints fresh `CharRun`s on any edited row, so identity-based ownership dies on the first keystroke. Without the lock, `from_room` drops anything inside a fill region and the edit vanishes silently at save time. (2) **A draft file IS a level file** — same schema, own directory (`~/.Vimny/drafts/`) — so publishing is a copy with no export step that can lose something, and a half-finished draft is diagnosed by the very validator that will judge the finished one (it simply fails `solvable` until it has a tape). **`:play` is the rehearsal and `:record` is the take.** Both PLAY the level rather than the bench; the only difference is that a rehearsal writes nothing down. That split exists because every take overwrites `solution`, so before it the only way to walk your own level was to gamble the tape you already had on solving it again — an author who merely wanted to feel the room out had to win perfectly or lose their route. `:play` passes `_record={'off': True}`, which keeps everything a take gives (fresh build, declared command set, the `_save_progress` guard, the stripped `admin` token) and skips only the capture, so an unwritable key is no longer a reason to end a run nobody is transcribing. It builds with the validator's par when the level has a tape — *is it doable in the budget* is the question authors actually have — and `:play!` drops the budget for a roam around a half-built room. `:e` inside a run of either kind reloads THE LEVEL BEING PLAYED, via a `rebuild` thunk on the recorder dict — `level` is only the slug the overworld opened the forge from, and rebuilding that answered *restart this* by dropping the author into the First Cave with their draft nowhere on screen. A rehearsal reloads on a NEW seed (the fills re-roll — that is the "what does someone else see" question); a take reloads on the level's own seed and clears the tape, because a tape holds typed letters and a re-roll mid-take would record a route through words no copy of the level has. The same branch now reloads under `_known` when the level declared one, instead of asking the curriculum about a slug it never had. **`:canvas <rows>x<cols>` grows the ground** (`format.resize`, crop's deliberate half). A draft opens on a 100x100 field of stone because you cannot select a region larger than the room you stand in — but that only helps drafts made since, and an author on an older or imported one was capped inside a rectangle they never chose. Crop can be silent because it only ever takes untouched stone off; growing cannot be, because nothing in a level says how much room its author still wants, so it is a command. Everything is anchored TOP-LEFT and the new stone goes on at the bottom and the right, so no cell, entity, fill region or mark changes coordinates and a tape recorded before the resize still plays — anchoring in the middle would invalidate every one of them. Shrinking is refused the moment it would cut content (border wall included) rather than dropping it. `:record` records by PLAYING: it never records in the editor (passable walls, no budget, no gating would yield a route no player could follow) but builds the level fresh and re-enters `run_dungeon` with `_record=` and `_known=level.known`, so an undeclared key is refused during the take rather than found by a stranger later. Recording stops at the win (`replay_tape` appends its own `:wq`), and `engine.tape.from_keystroke` REFUSES a key the notation cannot write (arrows, Backspace) rather than skipping it, which would hand back a tape that replays as something other than what was played. The recorded tape is GROUPED as it is captured — a space is laid down before any key read in NORMAL mode with the parse buffer empty (the first key of a fresh command), so counts ride with their motion, an operator with its target, and a typed word or `:`-line stays one unbroken run, matching the hand-authored karaoke sheets (`4E 2j ^ 2j $`). The spaces are separators (`engine.tape.strip_separators`), stripped on every replay/tokenise, so grouping changes only how the tape READS, never how it plays or the par it earns. A take runs under the author's own name, so every progress write inside `run_dungeon` goes through the `_save_progress` guard — unguarded, a rehearsal would overwrite the author's real save. Par still comes only from the validator's replay, never from the live session's count: one authority, identical to CI. Two rules keep a take honest, both learned from the first playtest. The `admin` token — which the forge's author always has, from the player name or the Warden's hat — makes `action_allowed` say yes to everything, so `run_dungeon` STRIPS it whenever `_record` is set; left in, the take records a key the level never declared and the level then fails for the first stranger who downloads it, destroying the one guarantee recording-by-playing offers. And **session entities never enter a level file**: the companion horse is placed into whatever room the player walks into, so `_draft is not None` bars him from a forge room and `format._TRANSIENT_KINDS` strips him on capture. He is not cosmetic there — a shipped horse re-fires the first-meeting naming PROMPT, which consumes the keys after it, so the trailing `:wq` of a recorded tape is swallowed and a level that plays perfectly reports itself unsolvable.

- **Two runtime rules an author can DECLARE (`Entity.drops`/`Entity.group`, `Room.seals`).** Both existed as hardcoded builder logic long before they existed as data, and both are now driven by generic ticks that `_content_ticks` runs for every level, shipped or downloaded, and that no-op when nothing declared them. (1) **`drops`** — "leave this behind when you die", written `kind` or `kind:tag`, with `group` making it wait for the last member of a group. The two prior implementations disagreed: `_on_kill` had a literal `level == 'goblin_gauntlet'` branch that only fires on `x` combat, so an editing delete (`dw`) dropped nothing, while the Operator's Vault used a per-turn tick recomputed from the live roster. `_drop_tick` is the second way, generalised off goblins and out of the level table. Its landing cell is the group's lowest `(row, col)` — derived from the FILE, so the key falls in the same place for every player and after every undo, rather than wherever the last one happened to die. `world.DROPPABLE` allowlists what may be dropped, and lives beside the field so the runtime and `vimny/sharing/validate.py` cannot read different lists: `drops` is the ONLY field in the format that creates an entity at runtime, so it is the only one where a downloaded file could otherwise hatch something nobody counted. (2) **`seals`** — a `world.Seal`: the cells in `opens` stand FLOOR exactly while the seal reads true. Same law as the family it came from — a reading recomputed every turn, never an event that fired, which is what makes `u` re-seal — plus the guard against re-walling the cell the player is standing in. It reads FLOOR/CORRIDOR only, so a target word on a wall plaque never satisfies its own door. Two asymmetries worth knowing: a seal cell is written out as STONE by `format.from_room` AND re-shut by `format.build`, independently, because an author is likely saving while looking at a door they just opened and a level must not ship with its puzzle already solved; and `validate` refuses an `opens` cell inside its own `region`, which would otherwise open, become walkable, get written on, and re-shut on whatever was written. Two later axes keep harder doors honest: under anyrow scope every `match` target must be proven on its OWN row (the distinct-row law — so `match=(t,t)` is the Y p duplication door: one verse satisfying both targets is one proof counted twice), and two column laws name WHERE a reading stands: optional `head: <col>` is the left-align law (a matched row's first glyph must sit at exactly that column — the << door, whose verse reads true at ANY margin because every reader deliberately ignores margins), while `at: <col>` is the pin law (the target's first glyph stands exactly at that column, west of it invisible — the Alignment Halls' plumb line, where insert-junk shoving a word onto the register is a legal route). A seal may name one or the other, never both. The forge speaks all of it: selection-free `:seal [xN] [@col] [|col] [*]<text>` arms a whole-floor door (`x2` duplicates the target, `@4` names the margin, `|16` pins the target — region form refuses all three), and `:final` bolts the exit cell behind every seal already in the level.

- **THE WRITING RULE (companion to the landing rule, 2026-08-02): a cell the cursor cannot stand on cannot be written into, and a verb that writes-and-advances stops at it.** The landing rule above covers the JUMPS. The verbs that write a cell and step to the next one — `i`/`a` (`insert_char`), `A` (`insert_char_extend`), `r` (`replace_chars`), `R` (`replace_overtype`) — asked only the CELL TYPE, and every door in the game stands on ordinary floor. So typing at the cell before a lock walked the cursor straight through it while `l` refused, and a player could **append their way past any door in the game** (it predates `fancy_door` and applied to `locked_door`, `seal_door`, `boss_seal` and `shield` alike). Charwise **paste** was the worse half of the same hole: `_place_row` clipped at walls only, so `p` laid text ACROSS a door, and since `op_paste` lands the cursor on the last pasted cell the player rode it to the far side. Both are fixed against one named set — **`world.BLOCKING_KINDS` + `world.blocked_by_entity`**, now also the source for `is_passable` and `_cross_water`, because a blocker only some readers know about is a hole in every wall it stands in. Two details worth keeping: the paste bound is on the WHOLE placement, not per cluster (a clip cut from a gappy row holds one run per cluster, and bounding each run alone still lets the run that BEGINS past the door land there); and `op_paste`'s cursor walk-back had to learn to skip the door too, or it read the door entity as "something pasted" and parked the cursor inside the lock. Held at a door, each further keystroke writes at the same cell and shoves its neighbour onto the door, where `open_gap` has always dropped it into the void — typing at a lock costs you the character, exactly as typing at any other brink does. Regression tests: `tests/test_fancy_door.py`, parametrized over all five blockers × all four writing verbs, plus the clustered paste.

- **A door blocks FEET and the EYE independently, and neither is terrain.** `door`/`locked_door` are entities standing on a floor cell — `:paint door` now says so by name rather than listing terrains, because "Unknown paint: door" beside a palette with no door in it reads as *this game has no doors*. Only `locked_door` is in `is_passable`'s blocker set; a plain `door` is walked onto and opened with `x`, and a barrier you break through is `:paint wood`. Sight is the other axis: the fog law is STONE-bounded on purpose (`motion._vision_flood` — a caged specimen has to be an exhibit, not a rumour), which left a level file unable to ask for darkness where there is no wall. `Entity.opaque` is that ask, carried by the door itself: the eye reaches the door cell and stops, so everything beyond starts fogged and OPENING the door is what lifts it — derived, never stored, so moving the door moves the darkness. `format.build` therefore indexes the room BEFORE applying the law; indexed after, `entity_at` answered None and an opaque door fogged nothing. The stop holds even when the eye BEGINS on the opaque cell: a plain door is walkable, so a player can stand on a closed opaque one, and `_vision_flood` must not exempt its own start cell or the far side lit up the moment a `$` landed on the door — a door that "un-fogs without ever opening it". Sight already won west of there is kept because fog is only ever lifted, so stepping onto the door reveals nothing new and stepping PAST it opens the pocket up to the next closed door. **`validate._check_operable`** covers the other half of the same report: a lock is opened by PASTING a key onto it (`p` east, `P` west — `x` alone only picks the key up), so a level declaring neither ships a door nobody can open. The author cannot see it, because the forge does not gate — hence one warning (the door and its key are the same missing lesson, said once) naming the cell. `:play` carries it IN as the played level's opening banner via `run_dungeon`'s `_notice` param, where the author is standing in the room it names, rather than pushing it back at the bench after the run; `_warn_display` strips the `[rule]` tag the tests key on and leads with a plain "Warning:".
- **A `fancy_door` is a door whose key is words you cut off the floor** (`Entity.password`, added 2026-08-02). Same gesture as a `locked_door` — stand beside it and `p`/`P` — but instead of a `floor_key` entity in the register it wants a register whose TEXT reads its password (`registers.clip_to_text`). It exists because a level that teaches one operator+motion pair per corridor could only ever punish a cut that took too LITTLE: leave a guard alive and he is still standing at the exit. Nothing punished a cut that took too MUCH, because **every creature a `dw` kills a `d$` kills too** — which is how the Operator's Vault shipped with `d$`/`d^` clearing six of its ten corridors for *less than par*, i.e. six decorative lessons. A fancy door is BOTH bounds in one entity — a cut that reaches too little hands it a fragment, a cut that reaches too far hands it the password plus whatever it swept up — so the guards had nothing left to do and the Vault was redesigned without them (2026-08-02). Note the geometric consequence, which is sharper than it first looks: a door can only be pasted into from the side the level's curriculum can paste toward, so a level holding `p` but not `P` must put every fancy door EAST of the player, whichever way its cut runs. In a level whose fog is DERIVED that constraint reaches the whole plan, because derived fog only stays dark while every way onward hangs behind a shut door — and a backward corridor cannot host its own door at all (its cut ends at the line head with no floor west to paste from). The Operator's Vault answers that by letting a backward corridor keep NO gate: it drops at the line head and its gate waits one row down at col 3, opened with the word the cut is still holding. A password in the register survives the trip, which a key on the floor would not — so the door being register-fed is what makes the whole snake gateable. `clip_to_text` is deliberately generous about WHITESPACE and nothing else: runs collapse and ends trim (so `dw`'s trailing space and `dd`'s forty columns of blank floor don't matter — those are differences in the motion, not in the answer), but an over-wide cut reads as extra words and no trimming hides it. **The check is on the REGISTER, never on the cells in front of the door** — otherwise a player could shove the right word into the doorway by inserting whitespace, and would be right, solving the level with an edit unrelated to its lesson. It is the same rule a locked door already keeps (a key lying *next* to one has never opened it), which is what lets this be taught as the familiar key-and-`p` model with a word for a key rather than as a new mechanism. The refusal quotes the REGISTER and only the register (*It hears "p1g" — and does not budge*): quoting the cut back is what teaches that the door weighs the whole of it, fragment or extra words and all, without needing a plaque to say so. It named the wanted password too until 2026-08-02; that was safe only while every password lay on the floor in front of its own door, which is true of the Vault and is not true of a door an author places in the forge with a word of their own. Drawn with its OWN glyph — `S.DOOR_SPOKEN` (`⍞`, APL's quote-quad: a box you speak into; `◫` where that measures wide) in the lock colour, in both orientations, because the shape is the door's identity and a padlock sends a player hunting for something to pick up when there is nothing to pick up. Its unlock beat is the locked door's beat with the key swapped for `S.KEY_SPOKEN` (`❞`, → `"`) via `_unlock_animation(..., icon=)`. Deliberately NOT emoji, and not `⌨` either: `🗣` and its neighbours measure one column and render as two in most terminals, which the width fallback cannot catch (it only sees the measurement), and `⌨` is emojified by enough terminals to have the same problem. In `_SCAN_BLOCK`/`_FOG_BLOCK_KINDS`/`CARET_TRANSPARENT`/`is_passable`'s blocker set. In the forge palette; because `:entity` splits on whitespace, a phrase password (the shape a line motion produces) is typed with underscores — `password=speak_friend_and_enter` — and stored, shown and compared as the phrase. The passwords themselves live in **`vimny/content/passwords.py`** (`PLAIN` / `SPLIT` / `QUERY` / `PHRASE`, plus `POOLS` / `POOL_OF` / `ALL`; `dungeon_gen`'s `_OV_*` names are aliases), sorted by SHAPE (which motion can take one in a single cut), and **every entry must be a real password from somewhere** — an invented one is indistinguishable from a real one to whoever adds the next, and the half-recognition the idea rests on quietly stops being real. `_OV_PLAIN` is shared: the Binder's Reliquary draws its far-shore pass-word from it too (2026-08-02), since a level whose fiction is a password reads better with a word the player may know than with generic vocabulary. That shore right-ALIGNS the word (`_BND_WORD_END`) because the pool's lengths differ and the route touches the word's tail, not its head. The **forge** offers the pools too (`_entity_choices('fancy_door', 'password')`, noted by pool via `_choice_note` — the shape is what an author needs, not the reference), phrases underscored because the picker hands its answer back as `:entity` text; the free-text row below the list is what keeps it a library rather than a menu. It offers the **level's own `:vocab` words FIRST** (`_pick_entity(..., custom=_draft.level.vocabulary)`) — the same pool `:fill custom` lays on the floor, since a door's password and the words in the room it stands in are one fiction, and a level that has declared a vocabulary has declared what it is about. A word in both is listed once and noted by its shipped pool, because the shape is the useful fact.
- **`:entity` is `:set`.** `:entity kind field=value …` places or configures the cell under the cursor, `:entity field=value` retunes what is already there, `:entity?` reads back non-default fields only, `:entity!` removes, and a bare `:entity` opens a j/k picker over `_ENTITY_PALETTE`. The picker is a VIEW of the command, never a second path — everything it can do is typed, and therefore recordable in a tape. The read/write/clear split matches the forge's metadata commands and the `:set wrap` the game itself teaches. `_ENTITY_PALETTE` is one table with three consumers (picker, validation, the no-argument listing); before it, the presets lived inside the handler and the list of kinds was a `'|'.join` in an error message, so the only way to learn what could be placed was to place something wrong. `_ENTITY_SETTABLE` deliberately omits running state (`ai_tick`, `move_dir`, `shade`) — offering it would only invite a level whose creatures start mid-stride — and `_entity_field` type-checks, because `hp=lots` would otherwise store a string on a dataclass that never checks and fall over long after the level shipped.

## Test conventions
- **`tests/conftest.py` is the order-of-run insurance.** Several long-standing tests stub collaborators by RAW assignment (`main.render_all = cap`, `Terminal.height = property(...)`) instead of monkeypatch; an autouse fixture there snapshots `main.render_all` and blessed's size properties at import and restores them after EVERY test, so alphabetical file order can never make one file's stub break another's assertions. New tests should still use `monkeypatch` — the fixture is a safety net, not licence.
- Dungeon tests: parametrize over `SEEDS = [1, 42, 999, 12345, 2**20 + 7]`; one test per property (reachability, par match, budget formula, command necessity, void safety).
- **Read-only property tests share builds via `tests.cached_room(builder_name, seed)`** (lru_cache in `tests/__init__.py`) — a dungeon is built once per (builder, seed) for the whole run. NEVER mutate a cached room; a test that simulates play calls its builder directly for a private copy.
- The budget formula (`budget == ceil(par × 1.4)`) and answer cost are asserted ONCE, universally, in `tests/test_answer_paths.py` (auto-discovered over every `build_dungeon_*`); don't add per-level copies. Two documented opt-out sets live there: `_NONSTANDARD_BUDGET` (a level with a deliberately tight/non-1.4 budget — e.g. the Change Annex's S2 volume forcing, where the margin must sit BELOW the trigger count so the all-old route overshoots) and `_ANSWER_NOT_TOKENISED` (a level whose canonical answer isn't a space-separated token string — e.g. change/substitute routes whose typed phrases contain spaces). Both pin their specifics in the level's OWN test instead.
- Command necessity: BFS with restricted command set; assert `cost > room.budget`.
- **Answer-tape notation.** The admin karaoke sheet matches keystrokes against `room.answer` with plain spaces stripped as display separators, so a literal space cannot stand for itself: a space the player actually TYPES is written `<Space>`, and a typed Enter `<CR>` (shipped examples: `gi<Space>{word}` in The Wet Ink, `:set<Space>nu<CR>` in The Culling Ledger). `vimny/game.py` substitutes `<Space>` before matching; `tests/test_answer_paths.py` maps both back when driving a tape. Multi-word typed text is therefore representable. Rooms with no meaningful tape (combat, arenas) set `room.answer = ''` and pin par with a driven test instead. **One command to a run**, the same grouping the forge's recorder produces (see above): counts ride with their motion, operators with their target, `f`/`F`/`t`/`T` with their character — `dw`, not `d w`. `tests/test_tape_grouping.py` enforces it by SHAPE (a run that could not be a whole command on its own is the defect) rather than by parsing, with three exceptions that only look dangling: a bare operator after a visual selection (`v 2j tn d` — the selection is its argument), `q` (the macro terminator, the one bare letter that means *stop*), and `0` (a motion, not a count). The Operator's Vault and The Beacon Tiers were hand-written split (`d w`, `y l`) until 2026-08-03; the spaces are separators so nothing about how they PLAY changed, but `_token_ks_cost` had no rule for a grouped `dF?` and had been silently charging 1 for three keys — a cost model that only agreed with the tapes because they were written wrong.
- File I/O tests: `monkeypatch.setattr('save.save_manager.SAVES_DIR', tmp_path)` to avoid touching `~/.Vimny`.
- Motion/editor tests: build a minimal `Room` fixture with `rebuild_indexes()` rather than using a full dungeon.
- Key files: `tests/test_counting_crypts.py` (template for level tests), `vimny/engine/motion.py` and `vimny/engine/editor.py` (source for motion/editor tests).
- **Browser-build tests run in a SUBPROCESS.** `web_terminal.install()` swaps `blessed` in `sys.modules`, and `vimny.game` binds `Terminal` at import — so the swap only takes in a process where nothing has imported the real blessed yet. `tests/test_web_terminal.py` unit-tests the shim in-process and shells out to `tests/_web_smoke.py` (underscore = not collected) for the end-to-end play-a-level check. The browser half is `web/test/*.mjs`, which is NOT part of the pytest suite: it needs node and a Chromium. `smoke.mjs` asks whether the game works, `lifecycle.mjs` what happens at the edges (quit, restart, reload, second tab, resize), `saves.mjs` how progress gets in and out of one origin's `localStorage`, and `keys.mjs` whether control keys reach the game — that last one **needs a real browser window** (`DISPLAY=:0`), because headless Chrome enforces none of the browser's own shortcuts and so cannot tell you whether Ctrl-W would have closed the tab. It answered that xterm.js cancels all eight itself, which retired a hand-rolled interceptor that had never once fired.
- **The dummy dungeon is a coverage invariant, not a level.** `build_dungeon_dummy` is a labelled showroom (west) plus a blank editing yard (east), and `tests/test_dummy_dungeon.py` asserts it holds ONE specimen of every `CellType`, every entity kind, every rune kind, and every glyph-CHANGING entity tag — guarded in both directions, so a new kind fails the suite until it is both placed and declared. Tags that only change behaviour (the warden ranks) are deliberately excluded: they all paint the same `W`. Two structural facts the layout depends on: label text lives in WALL cells (uncuttable, skipped by the floor text scans, so a stray `dd` cannot wipe a sign), and cols 1-3 are a floor SPINE without which those stone label rows would split the showroom into disconnected strips. Jails are stone on three sides with a `door` on the fourth — `apply_stone_fog` sees past a door so the specimen is on display, and `_steppable` refuses any cell holding an entity so the occupant can never cross it; the cage holds for exactly the reason the fog clears.

## Dead-code detection
- `python -m pip install vulture` once, then `python -m vulture` (config in `pyproject.toml`).
- Static analysis is blind to dynamic dispatch, so the config pre-ignores the `getattr`/slug families (`build_dungeon_*`, `_par_*`, color fns discovered by `vimny/render/color_palette.py`). A finding there is real.
- At `min_confidence = 60` it also surfaces *candidates* that need human triage: module-level constant tables (e.g. unused glyphs in `vimny/render/symbols.py`) and enum members (`RoomType.SAFE/BOSS`) read only via `S.NAME` attribute access or from tests can be false positives — verify with a `grep` before deleting.
- When verifying, grep RAW (`grep -rw NAME` over the whole repo, no `-v` filters): a filtered count once missed `T.keystroke_cost` — attribute-style access from tests reads exactly like noise until the suite falls over. Anything documented in this file (e.g. `POOL_OF`) is API whether or not the tree imports it.
- Complement with the produce/consume check for entity `kind` strings: a kind consumed (`.kind == 'x'`, `_entity_by_kind.get('x')`) but never produced (`Entity(kind='x')`) is dead dispatch — this is how the orphaned `keystone` mechanism was found.

- **VEILED PLAQUES ARE NOT FOG (`Room.veiled_cells`, `dungeon_gen._lay_dark`, `motion.unhide_region`).** Fog is the stone law: a physical fact about what the eye can reach, DERIVED from the walls, over the cells you could stand in (`_FOGGABLE_CELLS`). Three levels used to say it by putting wall cells into `fog_cells` (the Wet Ink's plaque quarters, the Manifold's and Scrivener's carved halls), and each one then had to be excused from every fog audit and from the round-trip probe — an exception per level, for a mechanic they shared. `veiled_cells` is the same implementation under its own name: the renderer draws a veiled cell as bare stone, and a level lifts it by discarding, exactly as fog is lifted. Use `_lay_dark(room, region)` to hide a mixed region — its floor is fogged, its walls are veiled, both true of their own cells — and `unhide_region(room, region)` to reveal it, which lifts both so no caller can lift one and forget the other. Both layers validate their pairs at parse (`_parse_cells_list`) rather than silently dropping junk. The FORGE paints both with ONE smart kind each: `:paint underwater` keeps whatever ground it touches — floor, corridor or channel — and adds the haze (over water the save rides `M` codes; over floor it lands in the coordinate list); over stone it is refused. `:paint veil` is its stone sibling — a carving not legible yet, refused on open ground. And the bolt law UNVEILS: a seal's `unveils` cells (forge `:bolt` splits the selection by kind — plain cells become doors, veiled cells become reveals) become legible exactly while the condition reads true, under the full bolt vocabulary — text-match, extinction, requires-chains — so authored secrets answer to data instead of needing a scripted tick. (Shipped levels keep their richer ticks: firelight-by-quarter and progress-gated halls are conditions a text bolt cannot say.) Misted text is legible through the weather (ink shows through — see Known bugs) but WEARS it: hazed glyphs render on `mist_bg`, the same lifted grey a discovered channel wears, so a player can tell at a glance that misted text is read-only ground — unstandable, unsearchable, uncutable.

## Known bugs
None currently. Previously known bugs (now fixed):
- **One open Shelving bolt unblinded the whole pocket.** The four gallery bolts open statelessly as each misfiling is mended, and the first open bolt handed the reveal flood a sightline down the gallery: the chest and exit past the still-shut bolts lit up, and G/gg teleported the player east across stone to the chest (fogged cells are impassable, so jumps could not land there — until the fog lifted). **Fixed 2026-08-23**: the sealed pocket rides the file's MIST as well as the fog — weather does not lift because a gap opened elsewhere on its row (`auto_fog_tick` never subtracts mist), every jump and scan gates on passability, and the tick unveils both sets only when the seal parts. `tests/test_shelving_room.py::test_one_open_bolt_never_unblinds_the_pocket` pins it; the level now round-trips whole (56 of 60).
- **Sunken text shipped invisible (`shelving_room`, `refrain_vault`).** The renderer's contract for underwater floor carrying a glyph was "readable in full colour but never standable, searchable, or cuttable" — but it gated the reading behind `_discovered()`, which demands an open, revealed neighbour, and the reveal flood stops dead at mist. Most of the Shelving Room's verses touch no open floor until the player edits them, and the Refrain's chasm (the `:1j|1y` yank source) is bordered only by walls and sunken water — so the par routes manipulated lines a sighted player could never see, and the par audit never noticed because replay plays blind. **Fixed 2026-08-23**: the haze hides TERRAIN, never WRITING — glyph-bearing mist renders from frame one; bare channels keep the gate (it hides the channel's shape, the leak it exists to prevent). Both levels are the curriculum's only glyph-bearing mist, so nothing else changes what it shows. Pinned by frame-capture tests in both suites.
- **Two creatures sharing a cell corrupted the entity index.** `Room.remove_entity`/`kill_entity` popped the cell slot unconditionally: killing an elf that had just dropped a coin onto its own cell erased the COIN's index entry, leaving it invisible to `entity_at` (uncollectable until some rebuild happened to save it). **Fixed 2026-08-21**: both pops are identity-guarded (`_entity_map.get((e.row, e.col)) is e`). Behavior change worth knowing: a coin dropped where you stand now pockets itself that same turn, because the pickup finally sees it — `tests/test_easter_eggs.py::test_x_an_elf_drops_gold` pins the new contract, `tests/test_world_spatial_index.py::TestStackedEntities` pins the indexing.
- **`a` could park the cursor inside stone.** Lowercase `a` advanced right unconditionally; from the last floor column it stepped ONTO the wall, where every insert-mode keystroke is swallowed in silence (only capital `A` builds ledges, via `insert_char_extend`). **Fixed 2026-08-21**: the advance is bounded by writable surface (`_PASTABLE` ∪ WATER); doors still work because they stand on writable floor.
- **`:m`/`:t` left the line's creatures behind — or cloned its boss.** Ranged row surgery snapshotted cells and glyphs only. **Fixed 2026-08-21**: `_snapshot_rows` carries live non-immune occupants as riders (fresh uids; `exit`/`entry_marker` excluded so position side effects cannot fire twice, and `edit_immune` excluded so `:t` cannot mint a boss copy).
- **Reflow drifted derived state**: `_shift_rows` moved cells but not `player.last_visual_anchor`/`last_visual_cursor`, `room.wood_damage`, or `room.torn` — post-shift frames rendered against stale anchors. Fixed 2026-08-21 (all shift with their rows).
- **`=` crashed on a whitespace-only verse**: a row whose only glyphs are spaces has a line extent but no words; the indent law split the empty string and raised IndexError. Fixed 2026-08-21 (guarded).
- **Hostile level JSON could allocate without bound, or crash with the wrong error**: `expand_row_mist` expanded run counts before checking them against the width (a `W99999999F` row allocated toward a billion cells); `loads()` let TypeError/KeyError/AttributeError escape as raw tracebacks instead of a named `LevelFormatError`. Fixed 2026-08-21 (bail before expanding; all confusion funneled to the named error).
- **A manifest row could aim downloads with a path-like slug** (`../../…`). Fixed 2026-08-21: slugs must match `[A-Za-z0-9_-]+`, enforced at listing AND again at install (belt and braces).
- **Renaming a draft onto another draft's file destroyed it silently** ('a b' and 'a_b' slug identically). Fixed 2026-08-21: `DraftNameCollision` refuses with a message; publishing over your own earlier publication (same name on the shelf) still iterates freely.
- **Save/layout writes were not atomic, and a corrupt save vanished silently from the roster.** Fixed 2026-08-21: `atomic_write` (tmp sibling + `os.replace` + best-effort `.bak`), `load_for` falls back to the `.bak`, and `list_saves` lists unreadable saves with a `_corrupt` marker — an adventurer who silently disappears is a player who cannot even ask what happened.
- **Idle content ticks fired every render frame** instead of once per turn (forge growth, ledger interest, shelving, refrain all raced at frame rate). Fixed 2026-08-21: gated behind the keypress — they advance at action cadence.
- **Custom levels ran under the `first_cave` slug**, polluting a shipped level's progress and tape records. Fixed 2026-08-21: they open under an inert `custom` slug, mirroring the forge's `community`.
- **HUD hearts disagreed between screens, and terminals without the fancy font drew fallback junk for key/chest glyphs.** Fixed 2026-08-21: all three renderers share `render.utils.heart_counts` (half-heart everywhere), and `⚷` / `▣` joined the ASCII-font fallback table for KEY/CHEST.
- **The Operator's Vault: a line jump skipped a lesson.** After corridor 1, `7G` landed in corridor 3 and corridor 2's `db` was never taught; `4G` tied `db h`. Pre-existing (the old geometry leaked one jump MORE). **Fixed 2026-08-01 by A PACK HOLDING ITS OWN DOOR**: a gate opens because its guards are dead, and the vault opens only when EVERY guard in the level is down — so a corridor you jumped over is a corridor whose guards still breathe, and the vault will not yield. **A jump kills nothing, which is why this beats a teleport where geometry cannot.** The jump still lands; it just does not pay. Two lessons in the fix: the test must measure OUTCOMES, not landings (the first version asserted no jump could *land* in an unopened corridor, which was both unachievable and the wrong question), and an errand a jump can run as well as a walk — here, fetching a dropped key — is an errand that cannot defend a lesson.
- `@` replayed only the FIRST line of a multi-line register (`registers.clip_to_keys` read `clip['rows'][0]`): fixed 2026-07-31 — every row is joined with ENTER, and a LINEWISE clip gets a trailing one, because a linewise register ends with a newline in vim (so `yy@"` on a line holding an ex command runs it *and* submits it). Latent since the macro/text stores were unified 2026-07-25: recordings are single-line, so nothing reached it, but a half-run macro fails silently — the first line executes and the rest vanish with no error. A single charwise row is byte-identical to before, which is what keeps every existing recording working (`tests/test_macro.py::TestMultiLineReplay`).
- `30l` trailing-zero split: fixed in `vim_parser.py` via `(count and buf[i] == '0')` guard. The same bug later resurfaced in the operator grammar (`d10w` parsed as `d0`+`w`) and visual text-object counts (`v10iw`) — fixed 2026-06-09 with the same guard in `_operator_target` / `parse_visual_textobj`. A count typed before a `"` register (`2"add`) was also dropped; counts now multiply (`2"a3dd` = 6 lines, Vim-faithful).
- `3j 59l 3k` void bypass: fixed — fog wall at door column blocks count motions past it.
- `x` then `u` left the character deleted (a free delete): fixed — the cut snapshot is taken BEFORE `_ed_cut` mutates the row, so undo restores the cut character.
- undo-refund cheat (`fx`·`u`·`;` / `/pat`·`u`·`n` / change·`u`·`.` reached the target for 1 key): fixed — undoing a find/search/change arms a re-cost (`player.pending_recost_f/s/c`) so the next `;`/`n`/`.` re-pays the full original cost.
- combat `x` (and shield `x`) pushed NO undo snapshot — `u` after a strike rolled back to the *previous* action's state: fixed 2026-06-09, each strike pushes its own `_snapshot` (undo revives the HP and refunds the key; `tests/test_undo.py::test_combat_x_undo_revives_hp_and_refunds_the_key`).
- heart-container stacking exploit (undo back past a pickup revived the heart while `max_hp` kept the +2 — snapshots don't carry `max_hp`): fixed — the pickup clears the undo/redo stacks (an undo barrier, like the seal door). Room transitions (entering/leaving the wardenverse) clear them too: snapshots can't restore a different room.
- visual-block `>`/`<` charged a keystroke and did nothing: fixed — `_apply_block` indents every spanned line (Vim behaviour).
